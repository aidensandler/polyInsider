Method

From wallet histories to testable predictions

A strictly chronological research design: define the hypothesis, freeze information at a pre-event timestamp, estimate the model, save the predictions and only then compare with the final outcomes.

Research design

1. Wallet skill is learned from earlier resolved events

For a wallet buying YES at price p, the outcome-relative price edge is y − p. For NO it is p − y. These contributions are averaged within each event so that one multi-market event is not counted many times as independent evidence. Wallets accumulate edge statistics only after the entire event has resolved.

2. Historical features are computed as of a frozen snapshot

For each market, the explanatory variables are the market price, direction of publicly observed wallet trades, how large those trades are, wallet evidence based on prior resolved events, and sample size. The processing code checks snapshot timestamps against resolution timestamps.

3. Train a forward-looking wallet model

At each earlier cutoff, summarize a wallet’s performance from fully resolved events. Label that wallet according to whether its mean signed market-price advantage is positive in a later set of resolved events. Fit logistic regression on earlier windows and evaluate on the last, untouched time window. The output is a probability of future above-price performance, not probability of possessing private information.

4. Fit a forecast of the YES outcome

A regularized logistic regression combines the log-odds implied by the market’s YES price, signed net trader flow, prior-skill-weighted flow, number of observed wallets and log total observed volume. Its output is a probability between 0 and 1. This is distinct from the older wallet-labeling test.

5. Evaluate later events and a market baseline

Train on earlier fully resolved events. Hold out later events, with all members of each event kept together. Check that the last training resolution precedes the first test snapshot. Report Brier score, log loss and AUC; compare the model with the market YES price at the same snapshot time.

6. Monitor unresolved events and keep an audit trail

Gamma lists active markets, while the Polymarket Data API v2 returns executed trades. Only public read-only requests are used. Before a market closes, the collector saves timestamped probabilities to an append-only CSV and a SHA-256 hash-chained JSONL audit file. Hash chaining detects accidental edits but is not a trusted third-party timestamp. Confirmed resolution labels are supplied separately at evaluation time.

7. Identify what is and is not established

Persistently successful wallets may be skilled, faster, better informed or simply lucky. The exercise cannot establish illegal trading. Current API snapshots are not historical order-book reconstructions, and taker-side trade samples omit some market participation.

The key standard: no trade, result, or resolution learned after a prediction timestamp may influence the features or fitting information available at that timestamp. The program checks this temporal separation and provides a persistent prediction log.
